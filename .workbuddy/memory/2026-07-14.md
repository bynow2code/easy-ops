## 修复：软件退出时未停止的脚本会变成孤立进程（非僵尸进程）
- 排查结论：进程树为 Electron Main → fork 后端 server → spawn shell 脚本。
  - POSIX（mac/Linux）：脚本以 `detached:true` 启动，是独立进程组 leader，父进程（后端）死后被 init 接管继续后台运行 → 孤立进程。
  - Windows：脚本 `detached:false` 是后端子进程；但 Electron `backendProcess.kill()` 底层是 TerminateProcess，只杀后端自身、不杀进程树 → 脚本残留。
  - 原 main.js `app.on('quit')` 只 `backendProcess.kill()`，从不杀脚本子进程，故确实存在该问题。
- 处理（双层防护）：
  1. server/index.js 新增同步 `killAllRunning()`（Windows 用 `taskkill /pid /T /F`，POSIX 用 `process.kill(-child.pid,'SIGKILL')`），并注册 `SIGTERM`/`SIGINT`/`exit` 钩子：收到 SIGTERM 先杀脚本再退出。
  2. electron/main.js 的 `app.on('quit')` 改造：Windows 改用 `taskkill /pid ${backendProcess.pid} /T /F` 连根拔起整棵进程树；POSIX 改发 `backendProcess.kill('SIGTERM')` 交给后端钩子去杀 detached 脚本组（不直接 kill(-pid) 以免误杀整个 Electron 树）。
- 说明：「僵尸进程」严格指已退出待回收的进程，此处实为「孤立进程」，但用户意图（退出后脚本不应继续跑）已解决。前端正常「停止」走 `/api/execute/:runId/stop` 不受影响。
- 验证：`node --check` 两个文件均通过。

## 验证：脚本结束/异常关闭/关面板/关软件 均不产生孤立进程
- 核心机制：前端关面板 = 关该脚本的 EventSource(SSE) → 服务端 `req.on('close')`（server/index.js:513-516 单条、:616-619 批量）→ `killChild` 整组杀（含脚本派生的子命令）。
- 逐条确认无孤立进程：① 脚本跑完 → `child.on('close')` 子进程已退；② 点 Stop → `/api/execute/:runId/stop` → killChild 整组杀；③ 关单面板（App.jsx:1296 关 ES）、关全部（handleCloseAllOutputs 遍历关所有 ES）、关浏览器/软件（浏览器 abort SSE / 上一轮退出清理）→ 均触发服务端 killChild。
- 已知非孤立细节（批量场景）：批量用「一个共享 EventSource `__batch__` + 共享 runId」。批量进行中关掉单个脚本面板时，关的是 `eventSourceRefs.current[script.id]`（实为 undefined），不会关掉共享批量流 → 该脚本继续后台跑直到整批结束或被 Stop/关全部触发；最终会终止，且软件退出时上轮清理也会干掉，故非孤立进程，仅是「关面板后仍隐藏运行」的取舍点。是否要把批量单面板关闭改为立即停该脚本（注意会停整批）待用户定夺。

## 进程泄漏复查（6 场景逐条核对）
- 机制总览：前端每开一个执行就建一个 EventSource(SSE) 连后端；后端 spawn 子进程并登记到 `runningProcesses`（按 runId）。清理触发点：① `child.on('close')`（跑完/被 stop）→ res.end；② 前端关 ES → 后端 `req.on('close')` → killChild 整组杀；③ POST `/api/execute/:runId/stop` → killChild；④ 软件退出 SIGTERM/SIGINT/exit → killAllRunning。
- 逐条结论：
  1. 正常结束：✓ 无泄漏（child 已退出，child.on('close') 清理）。
  2. 停止(Stop)：✓ 无泄漏（killChild 整组杀；批量因共享 runId 会停整批——设计如此）。
  3. 重新执行：✓ 无泄漏。`handleExecuteScript` 首行 `if (executingIds[id]||batchRunningIds[id]) return` 阻止运行中点重跑；跑完旧 ES 已在 'close'/'error' 里 `es.close()`+delete，新 ES 干净新建、新进程独立。
  4. close 关闭输出：
     - 4a 单执行关单面板：✓ 无泄漏（关 ES → 后端 req.on('close') → killChild）。
     - 4c 批量进行中关单面板：✗ **会泄漏**（隐藏运行进程）。批量用「一个共享 ES `__batch__` + 共享 runId」，单面板关闭逻辑只查 `eventSourceRefs.current[script.id]`（恰为 undefined），不会关共享批量流 → 该脚本子进程继续后台跑，直到整批结束 / 点 Stop（停整批）/ 关全部 / 软件退出才被回收。非永久孤立，但属于「关了面板却看不见仍在跑」的隐藏进程。
     - 4d 关全部：✓ 无泄漏（handleCloseAllOutputs 遍历关所有 ES，含 `__batch__`）。
  5. 批量执行：✓ 无泄漏（正常结束/Stop/软件退出均清干净；唯一漏点就是 4c）。
- 唯一真实漏点 = 4c（批量进行中关单个面板）。修复需把批量改为「每脚本独立 runId」才能单独 stop，属中等重构。是否要改待用户定夺。

## 修复「批量中关面板后重新出现」的瑕疵
- 现象：批量执行进行中点击某个正在跑的脚本的 Close，面板关掉后又因为后端的 `close` 事件被 batch `onmessage` 重建（`prev[scriptId]` 为 undefined → `if (curr && !curr.live)` 不命中 → 重建 `live:false` 面板）。
- 根因：上轮把批量单面板关闭改成「调 stop 杀进程树」，但共享 `__batch__` ES 仍存活，后端杀进程后回推的 `close`/`stdout` 事件会重建已删面板。
- 修复：新增 `closedBatchIds = useRef(new Set())`。① 批量 `onmessage` 顶部加守卫 `if (data.scriptId && closedBatchIds.current.has(data.scriptId)) return` 忽略已关闭脚本的所有事件；② Close 按钮 `isBatchRunning` 分支里 `closedBatchIds.current.add(script.id)` 再调 `handleStopExecution`；③ `handleBatchExecute` 起始与批量 `done` 时 `closedBatchIds.current.clear()` 清空，避免跨批次污染。
- 单次执行不受影响（Close 直接关独立 ES，后端事件不再到达前端）。
- 验证：`npm run build`（client）通过（仅预存 chunk 体积 warning）。
