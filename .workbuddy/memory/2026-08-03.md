## 开发模式 userData 与打包应用不一致（重要）
- 根因：`package.json` 中 `name: "easy-ops"` + `productName: "EasyOps"` 不一致。
  Electron dev 模式 `app.name` 取 `name` 字段 → userData=`%APPDATA%\easy-ops`；
  打包后 electron-builder 用 `productName` → userData=`%APPDATA%\EasyOps`。
  而 `scripts.json`/`shell-config.json` 路径由 `EASY_OPS_USER_DATA`(=app.getPath('userData')) 决定，
  所以 dev 会写到 easy-ops 目录，读不到打包应用创建的 EasyOps\scripts.json。
- 修复：`main.js` 的 `app.whenReady().then` 开头、未打包时
  `app.setPath('userData', path.join(app.getPath('appData'), 'EasyOps'))`，
  强制 dev 与打包应用共享同一份 userData（须在 ready 之后调用，setPath 在 ready 前会抛错）。

## 外部/旧版脚本配置强制归 Default 并自愈写回（用户需求）

    **强制全部归 Default**，忽略其自带 group 字段。

  （已规范则不改写，写盘失败不阻塞读取）。

## dev 模式列表仍为空 —— config.js 时序 bug（真根因，前几轮没打到）
- 现象：上一轮修了 server:dev 路径回退 + 导入裸数组后，用户用 `npm run electron:dev` 启动，
  脚本列表**依然为空**。但 `npm run server:dev` 单独起后端却能读出 20 条（上一轮已验证）。
- 诊断：写 `_diag_config.js` 复现 main.js 的 require 时序——
  先（env 未注入）`require('../server/config')`，再注入 `EASY_OPS_USER_DATA=EasyOps`，
  观察 `config.scriptsFile`。结果两处都打印 `C:\Users\bynow\.easy-ops\scripts.json`（带点、错误目录），
  `read()` 返回 0 条。
- 真根因：`server/config.js` 第 38 行 `scriptsFile: path.join(getUserDataDir(), 'scripts.json')`
  是**模块加载时 eager 求值**，而 `getUserDataDir()` 依赖 `process.env.EASY_OPS_USER_DATA`。
  `electron/main.js` 在**文件顶部第 13 行**就 `require('../server/config')`，
  而 env 注入在 `app.whenReady()` 回调第 211 行——早了一步。require 缓存把错误路径锁死，
  之后注入 env 也不生效。后果：Electron 内嵌后端读 `.easy-ops\scripts.json`（空）→ 列表空。
  ⚠️ 该 bug **dev 和打包后都存在**（打包 main.js 同样顶部先 require config）。
  之前 server:dev 能读 20 条，是因为 server/index.js 在 require config **之前**就设好了回退 env。
- 修复：`server/config.js` 把 `scriptsFile` 与 `log.dir` 改为 **getter 惰性求值**
  （每次访问按当前 env 求值，彻底消除时序耦合）。`getUserDataDir` 本就是函数，无影响。
  `server/index.js` 顶部注释同步更新（"必须先设 env 再 require"不再是硬性约束，仅保留习惯）。
- 验证：
  · 同 `_diag_config.js` 复现脚本重跑：注入 env 后 `config.scriptsFile` 正确变
    `C:\Users\bynow\AppData\Roaming\EasyOps\scripts.json`，`read()` 返回 20 条。
  · 真实 HTTP 冒烟：`EASY_OPS_USER_DATA=EasyOps PORT=4731 node server/index.js` 后
    `GET /api/scripts` → `ok=true, scripts=20, groups=["Default"]`（后端日志 scriptsFile 正确）。
  · `scripts-store` 测试 26 例全绿；改动的两个 server 文件 eslint 无 error。
  · 其余失败属预存、与本改动无关：`shell-routes` 4 例因 Windows 平台校验
    （fakeShell 非 Git Bash/WSL 被拒，断言文案是给非 Windows 写的）；useTheme 等 client
    测试/lint 因 eslint 扫到 client/ 下巨型生成文件 + 测试环境缺全局变量。均未触及。
- 教训（可复用）：Electron 主进程若在顶部 require 一个依赖运行期环境变量的配置模块，
  必须让该模块的路径类配置惰性求值（getter），否则 require 缓存会把错误回退路径锁死。
  此类 bug 用「复现 main.js 的 require 时序 + 注入 env 再读路径」的小脚本即可快速定位。

## 脚本执行完毕 → Completed 状态（用户需求：执行完要知道"已完毕"）
- 需求背景：当前是**交互式常驻 shell** 模型（脚本内容作首条输入喂入，脚本跑完停在提示符、
  会话不关、终端仍可读写）。`term.onExit` 只在整个 shell 会话关闭（Stop/关窗/exit）才触发，
  所以脚本跑完 UI 仍显示 Running，用户无法区分"正在运行"与"已执行完毕"。
- 方案（用户确认"加 Completed 状态"）：PTY 主机在脚本首条输入之后写一行唯一**哨兵**
  (`echo "EASYOPS_DONE_<randomHex>"`)，渲染层在输出流识别该 token → 状态翻 `Completed`
  （仅脚本结束、会话未关），并剔除哨兵回显/输出行，终端保持干净。光标停闪（沿用
  `cursorBlink = status==='running'`）、状态点变"已完成"、Stop 按钮在 Completed 时变为
  "End Session"（点它才真正 kill 会话）。
- 后端（已完成，前轮）：`electron/pty-host.js` `openSession` 引入 `crypto`，生成
  `doneToken`/`doneMarker`，脚本内容写入后 `term.write('\n'+doneMarker+'\n')`，返回值
  透传 `{ sessionId, doneToken, doneMarker, interpreter, args: [] }`。IPC 链路
  (main.js `pty:open` 直接 invoke 透传 / preload `pty.open`) 无需改，token 已能到渲染层。
- 前端改动：

  · 新增纯函数模块 `client/src/sentinelFilter.js`：`filterSentinelChunk(data, token, buf)`

## Bug 修复：移动分组后该组永久变灰（is-group-dragging 泄漏）

  · `handleReorderEnd` 补 `setGroupDragName(null)`（核心修复）；
  · 分组头 `<div className="script-group__head">` 加 `onDragEnd={() => handleReorderEnd()}`

## 终端每次执行后多余换行（修复 2026-08-03 晚）

### 症状
- 用户截图（ssh 远程拉取脚本）：脚本执行完后，终端出现 3 个 `bynow@ERAZER MINGW64 ~` 提示符 + 3 个空行，而不是预期的 1 个 PS1 + 1 个空行（脚本结束后 1 个、哨兵后 1 个）。

### 双根因
1. **`pty-host.js` 哨兵前多写 `\n`**：`term.write('\n' + doneMarker + '\n')` 中开头的 `\n` 让 shell 误以为用户提交了一行空输入，
   在脚本结束的 PS1 之外**额外**触发一遍"空提交"流程：shell 输出 PS1 + 一个空行 + 等下一个输入。
   所以原本的"脚本结束 PS1"变成"脚本结束 PS1 + 哨兵前 \n 触发的额外 PS1 + 哨兵 echo 后的 PS1"，共 3 个。
2. **`filterSentinelChunk` 整行 drop 哨兵回显行**：`$ echo "EASYOPS_DONE_…"` 含 token 整行被 drop，**把 PS1 第二行的 "$ " 也一起吃掉了**，
   导致第一个 PS1 显示残缺（只剩 `bynow@…~` 没有 `$ `）。

### 修复（前端 + 主进程两端）
- **`electron/pty-host.js`**：`term.write('\n' + doneMarker + '\n')` 去掉开头的 `\n`，改为 `term.write(doneMarker + '\n')`。
  哨兵 echo 命令直接紧跟脚本输入末尾提交后的 PS1，不再触发额外"提交空行"。
- **`client/src/sentinelFilter.js`**：
  - 哨兵回显行（含 `SENTINEL_HINT = 'echo "EASYOPS_DONE_'`）改为"**精细化处理**"：
    保留 SENTINEL_HINT 之前的 PS1 前缀 + 换行，丢弃 echo 命令部分 + 后续字符。PS1 第二行（如 "$ " 或 "% "）不再被吃掉。
  - `tail`（不完整尾行）处理升级：当 tail 含 `echo "` 开头但还没到 SENTINEL_HINT 时也识别为哨兵片段早期，
    把"已能确认的 PS1 前缀"立即写出、仅 echo 命令片段持到 buf 等待重组。避免 chunk 边界刚好切到 `echo "` 末尾时
    PS1 前缀延迟或丢失。识别条件：`echoIdx >= 0 && tail.length < 100`（哨兵 echo 命令总长度安全上界）。

## 编辑脚本时输出窗口滚动条"透过边界"渗到脚本页（修复 2026-08-03 晚）

### 症状
- 用户截图（Clipboard）：编辑脚本时，若执行脚本且输出窗口（exec panel）出现滚动条，
  会从右栏"透过边界"在脚本编辑页面上冒出一个滚动条。

### 根因
- `.right-region { display: flex; position: relative }` **没有 overflow:hidden**。
  它的两个子元素：`.panel--exec`（flex 子，常驻）+ `.editor-panel`（absolute 浮层覆盖）。
- exec 面板里：`.exec-list` 原生滚动条沟槽 + xterm 自带 `.scrollbar`（position:absolute）。
  这些滚动条元素一旦超出 exec 面板的 box，**没有任何硬边界阻止它们溢出右栏**——
  可能跨过 v-splitter 渗到左边的脚本列表 / 编辑面板边界。
- `.editor-panel { position:absolute; inset:0; z-index:5; overflow:hidden; opacity bg }`
  是"软保险"（盖住 exec），但若右栏无 overflow:hidden，exec 子元素的 overflow
  仍可越界（overflow:hidden 只裁剪编辑器自己的子元素，不裁剪兄弟 exec 面板）。

### 修复
- `client/src/styles.css` `.right-region` 加 `overflow:hidden`：把整个右栏变成硬裁剪框，
  无论 exec 面板的滚动条 / xterm `.scrollbar` 怎么折腾，都无法溢出到右栏之外，
  自然不会"透过"到脚本编辑页。配合编辑器浮层的不透明覆盖（软保险），双保险。
