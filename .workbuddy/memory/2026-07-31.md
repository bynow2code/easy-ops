## 修复 bug：WSL 下 tail -f 等持续命令「stop 失效」
现象：执行 `tail -f` 这类持续前台命令后点 Stop，进程杀不掉、命令继续在后台跑。
根因：Windows + WSL2 下执行命令是 `wsl.exe bash -s`，脚本内容（tail -f 等）跑在 **WSL2 轻量 VM 内的 Linux 进程**，不在 Windows 进程树中；原 killChild 在 Windows 走 `taskkill /pid <wsl.exe_pid> /T /F` 只杀到 Windows 侧的 wsl.exe，**杀不到内部的 tail** → stop 失效。Git Bash（msys2 子进程是 Windows 进程）/ macOS / Linux（进程组 kill）本就不受影响。

修复（server/index.js，仅对 WSL 生效，其它 shell 零改动）：
- 新增 `isWslShell(sh)`：win32 且 shell.id 以 wsl 开头或 command 含 `wsl(.exe)`。
- 执行时（execute-stream + batch-execute-stream）若 isWsl，向 stdin 先写 `echo $$ > /tmp/easyops_run_<runId>.pid\nexec bash -s\n`，让外层 bash 记录自身 PID（exec 后不变）供 stop 定位进程树；runningProcesses 登记加 `isWsl` 标记。
- 新增 `killWslRun(runId)`：通过「再起一个 wsl 进程」在 WSL 内部 `pkill -TERM/-KILL -P <pid>` 杀整棵进程树（含 tail -f），TERM→0.3s→KILL 升级，结束删 pid 文件；spawn 异步不阻塞 stop 请求。
- stop API 与两处 `req.on('close')` 主动停止时调用 killWslRun。
- 连带修复 terminated 误判：WSL 下 wsl.exe 是「内部被杀后自己 exitCode 退出」而非被信号杀，原 `terminated = code===null && !!signal` 误显示 Exit 1；新增 `forceStoppedRuns` Set 标记主动停止的 runId，close 事件据此正确显示 Stopped。

真机验证（本机 WSL 2.7.11.0 = WSL2）：执行 `sleep 31337`（类比 tail -f），stop 前 WSL 内 pgrep 可见该进程、stop 后已消失（证明内部进程被杀）；close 事件 `terminated:true`。客户端无需改动。重新 esbuild 打包 server/dist/index.cjs 并复制 scripts.json。

## ⚠️ 修正上面那条「WSL stop 修复」：之前的修复其实是无效的！
用户反馈 stop / stop all 仍杀不掉 tail -f。隔离复现 + 真机排查后确认，**上面那条修复的两个核心假设都成立、但实现落地时有 bug，导致内部 kill 永远是空操作**：

实测发现的两层根因（任一没规避都会静默失效）：
1. **WSL 内 `$(cat /tmp/pidfile)` / `read` / `<` 重定向读刚写的文件 → 返回空字符串**（本机 WSL2 bash 怪异行为，standalone `cat` 输出正常但 `$()` 捕获为空）。所以 `P=$(cat pf)` 拿到的 P 永远是空 → killWslRun 整段不执行。pidfile 方案在本环境根本不可靠（/tmp 写入读取也不稳定）。
2. **`pkill -P <父pid>` 按父子关系杀不可靠**：若 Windows 侧 taskkill 先把 wsl.exe 杀了，WSL 内 bash 死亡、tail 被 reparent 到 init，`pkill -P` 再也匹配不到 tail → tail 残留。

正确修复（已落地 server/index.js，重打包 dist，真实 server 端到端验证通过）：
- 执行时由 WSL 内 bash 把「组内 leader Linux PID」经 **stdout** 回传：`echo "___EASYOPS_WSL_PID___=$$"`（node 从 stdout 解析存入 `wslPidByRunId`，并用 `makeWslStdoutFilter` 剥离该标记行避免污染输出；过滤器保留 carry 以应对标记被拆 chunk 的极端情况）。stdout 捕获稳定可靠。
- stop 时 node 把该 PID **作为命令行参数**传入 `wsl.exe bash -c 'kill -TERM -"<pid>"; ...; kill -KILL -"<pid>"'`，用**进程组整组杀** `-<pid>`。进程组在成员未全退前一直存在，即使 bash 已被 reparent 也能精准命中 tail。
- 删除旧的 `WSL_PID_FILE` / pidfile 写入 / `pkill -P` 逻辑；`killWslRun` 改为读 `wslPidByRunId`（无 PID 直接 return 退回 taskkill 兜底）。`wslPidByRunId` 在 close 事件里自然清理。

验证：用隔离 `SCRIPT_DATA_DIR` 起真实 `server/dist/index.cjs`，SSE 执行 `tail -f` → 调 `/api/execute/:runId/stop` → WSL 内 pgrep 确认 tail 已消失（含「taskkill 先杀 wsl.exe + 延迟再内部杀」的对抗竞态场景也通过）。详见 MEMORY.md「执行停止（killChild）的 WSL 坑」段。

## 修复崩溃：后端进程以 exit code 1 退场（SSE 断开 + 停止时）
现象：用户跑脚本后断开 SSE（前端停止），日志尾部出现 `[Main] Backend process exited with code 1`，整个应用后端死亡。kill 桥接本身生效（已用 Git bash 桥接杀掉进程组 pid=1849），但随后后端崩了。

根因（后端无全局 uncaughtException 兜底，任何未捕获异常都会 exit 1）：
- **主因**：`killViaShellBridge` 里 `spawn(shell.command, ['-c', killScript], ...)` 这个桥接子进程**没有挂 `.on('error')` 监听**。该 spawn 在 `req.on('close')` 里被触发，一旦它异步失败（命令瞬时不可达 / 进程正在被回收等），会以「未捕获的 'error' 事件」抛出 → 直接带崩后端。`child_process` 的 'error' 事件若无监听即致命。
- **次因（潜在）**：`server.on('error')` 里 `process.exit(1)` 对「已开始监听后的连接级错误」（如客户端异常断开 ECONNRESET）也照杀，一次前端断连即让后端退场。

修复（server/index.js，已重建 dist 同步）：
- `killViaShellBridge`：把 spawn 结果存到 `bridge`，挂 `bridge.on('error', e => console.warn('桥接进程异常（已忽略）...'))`；桥接失败还有 killChild 的 taskkill 兜底，不影响主流程。
- 新增后端级 `process.on('uncaughtException')` / `process.on('unhandledRejection')`：**只记录完整错误栈（进 main.log）并继续运行**，不再让单请求异常杀死整个常驻后端。这同时把今后任何同类崩溃从「沉默的 exit 1」变成可见的 `[EasyOps][FATAL]` 日志，便于定位。
- `server.on('error')`：`process.exit(1)` 改为仅当 `!server.listening`（真正的启动监听失败，如端口被占）才退出；监听后的连接错误只记录不退出。

验证：dev 模式 `electron-dev` 直接加载 `server/index.js` 源码（无 `server/index.cjs`，main.js 回退到源码），改源码下次起 Electron 即生效；打包模式走 `server/dist/index.cjs`（已重打包）。grep 确认 bundle 含三处新逻辑。建议用户重跑「执行脚本→停止/断 SSE」并观察：若仍有异常，main.log 里会出现 `[EasyOps][FATAL]` 带真实栈，便于精确定位。
