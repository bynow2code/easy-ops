## 启动偶发「未检测到可用 Shell」→ 崩溃弹窗（已修复）

**根因（两个）：**
1. **偶发误判**：`server/index.js` 的 `detectShell()` 在 Windows 上用 `execSync('"C:\\Windows\\System32\\bash.exe" -c "echo test"', {timeout:1000})` 去跑 bash 来判断 WSL。WSL 冷启动常 >1s，被 1s 超时判失败 → 明明装了 WSL 却偶尔被判为「无 Shell」。且同步阻塞拖慢后端启动。
2. **崩溃**：`const shell = detectShell()` 没有任何 try/catch 兜底。一旦 detection 抛未捕获异常，后端进程直接挂 → 主进程 `backendProcess.on('exit')` 立刻 `showFatal` 弹窗（这正是「没检测到 shell → 程序报错弹窗崩溃」的弹窗）。

**修复：**
- `detectShell()` Windows 分支改用**快速、可靠**检测：WSL 用 `where wsl.exe`（毫秒级，不启动虚拟机），Git Bash 用 `fs.existsSync` 文件存在性判断；不再实际执行 bash。真正冷启动只发生在用户首次执行脚本时（一次性，可接受）。
- `const shell = detectShell()` 外包 try/catch：检测失败降级为「无 Shell」模式（command:''），应用照常启动、仅脚本执行不可用，**绝不崩溃**。
- execSync 的 stderr 全部设为 `'ignore'`，避免后端日志出现无关告警噪声。
- 前端 `App.jsx`：① 顶部新增醒目横幅提示「未检测到 WSL / Git Bash，脚本执行不可用」；② `handleExecuteScript` 与 `handleBatchExecute` 在 shell 缺失时**直接给出友好提示**、不再发起 SSE（避免后端回传 cryptic 报错）。
- 主进程 `electron/main.js` ready 握手兜底超时 5s → 20s：避免极慢机器上检测仍略延迟时，提前加载页面触发 `did-fail-load` 崩溃弹窗（后端真挂时 exit 事件会立即走 showFatal）。
- 实测：沙箱（wsl.exe 存在）`/api/system-info` 正确返回 `shell.command="wsl.exe"`；后端正常发 `ready`；前端 `vite build` 通过（403 模块）。

## 收尾暗病修复：`isUpdateRelatedError` 正则过宽（已修复并验证）

- **根因**：`electron/main.js` 的 `isUpdateRelatedError` 正则含裸词 `update` / `release`。这两个词出现在无数普通崩溃信息里（如 `failed to update cache`、`release the port failed`、`Cannot read properties of undefined (reading update)`），导致这些**真实崩溃被误判为「更新相关」而静默吞掉**，用户只看到程序莫名退出，反而更难排查。
- **修复**：正则只保留更新器【特有的、具体】签名 —— `Cannot download` / `net::` / `ERR_UPDATER` / `Update check failed` / `electron-updater` / 网络层错误码（`ECONNREFUSED|ETIMEDOUT|ENOTFOUND|ECONNRESET`）/ `status\s*\d{3}`。真实更新错误仍被过滤（已在 update modal 展示过），普通崩溃一律弹 fatal 弹窗。
- **验证**：`node --check` OK；7 个行为用例全部 PASS（3 个真实更新错误被过滤、4 个含 update/release 的普通崩溃正确弹窗）。

## 启动串台 bug 修复：同时开两个 Electron 应用 → 界面显示别的 App（已修复并验证）

**根因**：`electron/main.js` 从固定区间 `3001-3100` 探测端口并 fork 后端，20s 超时兜底 `resolve(port)` 用的是「探测端口」而非后端实际绑定的端口；`server/index.js` 同样在固定区间探测，撞车时改用区间内另一端口并通过 `ready` 回传。
- 两个 Electron 应用（本项目 + 用户另一个 Electron 项目）同时启动，会各自探测到同一个「空闲」端口、又各自 fork 后端去抢；失败方回退到错误端口 → 渲染进程加载到另一个应用的端口 → **界面串台**。前端本身用同源相对路径（`/api/...`），故根因纯在主进程 load URL 用错端口。

**修复（彻底去固定端口）**：
- `server/index.js`：删除 `PORT_RANGE_START/END`、`isPortAvailable`、`findAvailablePort`、`net` 依赖（死代码清理）。`startServer()` 改为 `app.listen(requestedPort=0)` 由**操作系统分配唯一空闲端口**，监听成功后读 `server.address().port` 作为真实端口，写入端口文件并 `process.send({type:'ready', port: actualPort})`。启动时先 `unlinkSync(PORT_FILE)` 清空旧值，避免主进程兜底读到旧端口。
- `electron/main.js`：`startBackend()` 不再探测固定区间，直接 `fork` 并传 `PORT:'0'`；`ready` 握手严格用 `msg.port`；20s 兜底改为读取【本应用自己的端口文件】（内容为【本后端】真实端口），仍拿不到则弹启动失败，绝不再用猜测端口去加载（杜绝串台）。

**验证**：`node --check` 两个文件 OK；单实例 fork 实测 `ready port=62915`（落在临时端口段、非 3001-3100），端口文件一致；**并发双实例**实测两后端拿到不同端口（63538 / 63539），无冲突。测试脚本用完即删。

**对其他项目的影响**：本修复让 EasyOps 始终用 OS 分配的临时端口，不会再与别的 App 争抢固定端口，串台问题在 EasyOps 侧彻底解决。但用户「另一个 Electron 项目」若仍用固定端口，自身仍有争抢风险——需对该项目做同样改造（监听端口交给 OS 分配，主进程只用后端回传的真实端口）。

## 打包崩溃修复：Cannot find module 'express'（已修复并验证）

**现象**：用户机器上 `D:\Program Files\EasyOps\resources\server\index.js` 启动即报 `Cannot find module 'express'`，应用弹 FATAL 启动失败。日志里 `port 3001` 说明他装的是【旧构建】（早于 OS 随机端口修复 + 早于本次修复）。

**根因**：`server` 的依赖（express/cors）装在 `server/node_modules`，靠 `package.json` 的 `extraResources` filter `["**/*","node_modules/**/*",...]` 期望被打进 `resources/server`。但 electron-builder 26 在打包 `extraResources` 时会做【生产依赖裁剪】：它只看 app 主入口（`electron/main.js` 不 require express）→ 把 `server/node_modules` 整体裁掉。构建日志实锤：`cannot find path for dependency dependencies=["cors@undefined","express@undefined"]`。曾尝试把 express/cors 加进根 `dependencies`，但 electron-builder 按「app 是否用到」剪，仍无效。

**修复（彻底去 node_modules，改用 esbuild 单文件打包）**：
- 新增 `devDependencies: esbuild`；新增脚本 `build:server`：`esbuild server/index.js --bundle --platform=node --target=node20 --format=cjs --outfile=server/dist/index.cjs` 并把 `server/scripts.json` 拷到 `server/dist/`（`__dirname/scripts.json` 运行时需要）。
- 所有 electron 构建脚本（`electron-dev` / `electron-build` / `electron-build-dir` / `electron-build-mac-*`）都先跑 `npm run build:server`，再 `electron-builder`。
- `extraResources` 由 `{from:"server"...}` 改为 `{from:"server/dist", to:"server"}`：打进 `resources/server` 的只有 `index.cjs`（1.1MB，express/cors 全内联）+ `scripts.json`，【不再有 node_modules 可裁】。
- `electron/main.js` `startBackend()` 的 fork 入口改为优先 `serverDir/index.cjs`、回退 `serverDir/index.js`（dev 未打包时）。

**验证（全部通过）**：
- `npm run build:server` 成功产出 1.1MB 单文件；`node --check electron/main.js` OK。
- 实测打包后端：监听 OS 随机端口、`/api/system-info` 正确返回（含 `shell.command="wsl.exe"`），证明 express 已完整内联、零 node_modules 依赖。
- `electron-build-dir` 解包构建：`resources/server/` = `index.cjs` + `scripts.json`，无 node_modules；构建日志不再有 `express@undefined` 报错（仅 `duplicate dependency references` 信息提示，无害）。
- **结论**：用户需重新 `npm run electron-build`（或 `-mac-*`）打包并重新安装，覆盖 `D:\Program Files\EasyOps` 下那版旧构建即可根治。

**注意**：`server/dist/` 是构建产物，建议加进 `.gitignore`（本次未改 .gitignore，留待用户）。
