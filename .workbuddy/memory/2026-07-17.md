## 修复：点击执行后一直卡在 "Waiting for output..."
- 症状：部分 Win11 配好 WSL2 的机器，点击执行后界面永远停在 "Waiting for output..."（SSE 已建立、后端 15s 心跳保活，但既无输出也不退出）。
- 根因：
  1. `spawn('wsl.exe', ['bash','-s'])` 经管道把脚本喂给 stdin；WSL 对「非 TTY 管道 stdin 的 EOF」转发有 bug，bash 一直等输入 → 不执行/不退出/不输出。
  2. `detectShell()` 仅用 `where wsl.exe` 判定 WSL 可用；但 Win11 自带 wsl.exe（Store 别名），即使没装任何发行版也命中，于是跑去跑一个会卡在「发行版首次安装交互等待输入」的命令。
- 修复（`server/index.js`，纯后端）：
  - **文件方式执行**（用户建议）：新增 `writeScriptTempFile` 把脚本写到系统临时目录，`buildExecArgs` 在 spawn 时把临时文件路径作为参数传入。WSL 走 `wsl.exe bash /mnt/c/.../script.sh`（用 `toWslPath` 转 Windows 路径为 WSL 路径），Git Bash/POSIX 走 `bash <filePath>`，彻底绕开 stdin EOF bug。执行命令优先用 `shell.fullPath`（appinfo 里检测到的真实 wsl.exe 路径）。
  - **真发行版探活**：WSL 分支在 `where wsl.exe` 命中后，再用 `wsl.exe -l -q`（毫秒级、不拉 VM）确认有已安装发行版；没有则跳过 WSL，降级到 Git Bash / 无 Shell（前端弹横幅、执行被守卫拦截，不再跑会挂死的命令）。
  - **看门狗**：单条与批量执行各加 `EXEC_WATCHDOG_MS=20000` 定时器，N 秒内无任何输出且进程仍在运行则强制 kill 并回送明确报错（提示 `wsl --install`），把「无限等待」转为可操作的报错。
  - **临时文件清理**：`close`/`error`/看门狗触发/写文件失败时均 `fs.unlinkSync` 删除临时脚本，无泄漏。
  - **输出解码**：`decodeBuffer` 仅在缓冲区以 UTF-16LE BOM(FF FE) 开头时才按 UTF-16LE 解码，否则 UTF-8。原先「奇数位全 0 就当 UTF-16」的启发式会误判含中文的 UTF-8 导致乱码，已修正（仅 BOM 判据，绝不污染正常 UTF-8）。
  - 删除旧的 `child.stdin.write/end` 与 `shell.args=['-s']`（执行不再用 stdin）。
- 验证：
  - `node --check` 通过。
  - 单测 + 集成测试：toWslPath / buildExecArgs(wsl 与 gitbash) / decodeBuffer(BOM 与 UTF-8 中文不误判) 全部 PASS；集成模拟「写临时文件→spawn bash <file>→捕获 stdout/stderr→exitCode 透传→临时文件清理」PASS。
  - 沙箱为 win32 且带假 wsl.exe，无法真跑 WSL 路径；但核心 spawn+流式+清理逻辑与 WSL argv 构造均已验证。真机需一台配好 WSL2 发行版的 Win11 验证端到端。

## 更正：撤回「WSL 管道 EOF 转发有 bug」的结论（重要）
- 用户质疑「你确定是 WSL 对管道转发有 bug？我的电脑就没问题」——质疑成立，原诊断不严谨。
- 逻辑证伪：若 wsl.exe 中转 stdin 管道真有 EOF 转发通用缺陷，则**所有装 WSL2 的机器都会卡**，不会只挑「某些电脑」。用户机器正常即证伪「通用 bug」。
- 修正后的准确结论：
  - 文件方式执行仍**保留**，但定位是「**更稳健的实现**」（绕开 Node spawn → wsl.exe 两层转换下 stdin 的编码/时序不确定性），**不是**「修了 WSL 的 bug」。
  - 「某些电脑」卡住的真实根因更可能在 **wsl.exe 自身**：`where wsl.exe` 假阳性 + 无就绪发行版 → `wsl.exe bash` 挂在发行版首次安装/交互等待，根本没走到 bash。
  - 真正解决卡死的关键是 **`wsl.exe -l -q` 真发行版探活 + 看门狗**，而非「从管道改文件」这一步本身。
- 已把 `server/index.js` 中所有「规避 WSL 管道 EOF 转发 bug」的武断注释改为中性、准确的措辞（明确标注「这不是修 WSL 的 bug」）。`node --check` 通过。
- 教训:不要把「没查清的现象」包装成「上游的 bug」;归因需能解释「为何只有部分环境复现」。

## 前端布局:单个输出窗口自适应高度(改正之前的理解错误)
- ⚠️ 之前理解错了:用户说的不是「列表容器」自适应,而是**单个输出窗口(.output-panel)**。列表容器(.right-panel/.outputs-container)应保持「现在的固定高度」(占满右栏、内部滚动)不变。
- 正确需求:① 单个窗口、空间足够时填满容器(不再死守 100px);② 多个窗口时自动**平分**容器空间(等长);③ 若平分后高度 < 当前窗口固定高度,则**停止平分**,各窗口保持当前固定高度、由列表滚动。
- 实现(纯 CSS,flexbox,`client/src/App.css`):
  - `.right-panel .output-panel`:`flex-shrink:0` → `display:flex; flex-direction:column; flex:1 1 auto; overflow:hidden;`。`flex:1 1 auto` 让其参与平分;`min-height:auto`(默认)使其**不能收缩到内容高度以下**,即「当前固定高度」= 兜底下限。
  - `.output-header` 加 `flex-shrink:0`(表头固定);`.output-section` 加 `flex:1 1 auto; min-height:0; display:flex; flex-direction:column;`(输出区随窗口伸展);`.output-section-label` 加 `flex-shrink:0`。
  - `.output-content-wrapper`:`height:100px` → `flex:1 1 100px; min-height:100px;`(内容区以 100px 为下限,窗口拉长时跟着伸展露更多输出)。
  - 行为验证(逻辑):设当前窗口高 H≈152px、容器可用 A、窗口数 N。A≥N·H → 各窗口 = A/N(平分/填满);A<N·H → 各窗口触底于 H、列表滚动不平分。完全契合需求 ①②③。
- 注:之前那版「列表容器自适应」(right-panel align-self/height/max-height、outputs-container flex:1 1 auto、媒体查询还原)已被外部编辑回退,本版未采用。
